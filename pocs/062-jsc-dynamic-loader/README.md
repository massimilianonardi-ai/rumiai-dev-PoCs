# 062 — Experimental `jsc` and classic-script dynamic loader

This is a **PoC**, not a released `m` command/library, a design contract, or an ESM compiler. It deliberately explores a model where several **ordinary classic JavaScript sources** are joined into **one classic browser JavaScript bundle**. A small explicit module descriptor supplies names, dependencies and source paths. The loader registers factories, evaluates them only on first `require`, and can replace factories and invalidate their transitive instantiated consumers.

## Compiler / dynamic-loader responsibility (experimental)

`src/jsc.mjs` is **only a compiler**: it produces classic module registration code and does not copy or implement the runtime. `src/loader.js` is the independent browser/runtime library that owns module registration, lazy evaluation, dependency invalidation, script transport and disposal. Its existing `JscRuntime` interface is currently a PoC compatibility boundary, not a promoted production API. The library also accepts manually authored module registrations without using the compiler.

Choose separate runtime and compiled scripts for development/patching, or package them as one JavaScript file for distribution using the **separate experimental** `src/assemble.mjs` helper. That packaging helper runs the compiler and combines its output with the unchanged runtime library; it does not make `jsc` a dynamic loader. The combined file remains useful under `file://`. The compiler-only output is *not* standalone and expects the independent loader to be present first.

ES Modules remain an entirely separate authoring/runtime path. This experiment never interprets them as `jsc` modules.

## Source contracts (experimental)

- `example/modules.json` has `version:1` and an array `modules: [{id,file,deps,format?}]`. The optional `format` can only be `classic`. The compiler explicitly rejects ESM format declarations and static `import` / `export` statements; no ESM reinterpretation or translation. Explicit browser-native dynamic `import()` expressions, if written in a classic source, are not transformed or controlled by the `jsc` registry and are therefore outside the managed loading contract.
- Each `.js` source is a function body receiving `require`, `module`, `exports`. Only declared dependencies may be requested; exports use `module.exports` or `exports`.
- An optional **assembled distribution artifact** includes the separately maintained loader and the compiler's module registrations. The compiler-only output contains no loader. Evaluation is lazy even though download is not: the single file must still be transferred in its entirety.
- `JscRuntime.installBatch([{id,deps,factory}, ...], {expectedRevisions?})` validates the **entire proposed graph** (including forward references, missing dependencies and cycles) and optional per-module expected revisions before any active instance is touched. On a valid batch it disposes affected active consumers once, consumer-first, then commits all definitions without permitting reentrant module API operations. `install` is the single-module convenience form of that operation. Valid replacements invalidate the updated module and instantiated dependents, calling `module.onDispose`. Clients **must reacquire** exports: already-captured exports are not live-updated. Invalid source syntax must be rejected by compilation before deployment; the runtime cannot undo external side effects from scripts that execute and throw.
- **Rollback scope:** invalid batches and stale revisions are rejected without changing existing definitions or live instances. Once cleanup callbacks begin, externally visible side effects are not reversible. If a disposer throws, planned definition changes still commit coherently, but `AggregateError` reports that a full application reload may be necessary; this is **not** transactional rollback of DOM/timers/user state.
- The compiler emits a single `installBatch` registration for all compiled module definitions; the optional external packaging step combines this with the independent loader for first-page distribution. When patching a page with an existing runtime, load **compiled registration code only**, not a second copy of the loader. Browser patch scripts should likewise use one `installBatch` call, not a sequence of individual `install` calls. Browser transport supports `loadScript(url, {expect: ['a','b']})` to verify both modules advanced, but it cannot roll back arbitrary script side effects.
- `JscRuntime.revision(id)` returns a per-registered-module install revision and resets to zero upon removal. With `JscRuntime.loadScript(url, {expect: id})`, a network request is not reported successful merely because the `<script>` tag loaded: it must actually install the expected module. No cryptographic content integrity or transactionality is claimed.
- `JscRuntime.remove` refuses removal when another registered module depends on the target.
- Cyclic dependencies are rejected during a `jsc` build; runtime initialization cycles are also rejected. Batch registration is coherent at the definition level; state restoration, migration and full rollback of external side effects are **not** supported.
- This classic module contract is not native ESM and does not claim direct legacy `m.Class` compatibility. Independent ESM toolchains may be compared at distribution boundaries, but `jsc` must not reinterpret ESM semantics.

## Freshness and release consistency are different concerns

A development server must send `Cache-Control: no-store` for reloadable source scripts. The browser's classic `<script src>` transport has no `fetch()` cache-mode override; this PoC's `loadScript()` relies on server headers and does not use POST or `eval`. Plain `fetch(url, {cache:'no-store'})` can obtain up-to-date source text but does **not** directly execute it under restrictive CSP without another execution transport.

For a web deployment, use revalidated HTML/release metadata (`Cache-Control: no-cache`), content-hashed immutable assets, atomic publication of complete release assets, and retention of assets referenced by still-active clients until migration. Server cache headers cannot by themselves upgrade JavaScript already loaded and executing in an open page. Service workers require separate update/version policy; avoid incompatible old HTML/new JS mixes.

## Limits requiring real follow-up

- Not yet a replacement for esbuild, Rollup or webpack: no ESM syntax, AST dependency analysis, CSS, source maps, minification, cross-package resolution, npm graph or tree shaking.
- `module.onDispose` only calls user-registered cleanup; external references, DOM/event subscriptions not cleaned by the module, network resources and other retained objects still require discipline. Runtime cleanup callback failures are aggregated; no atomic rollback is provided.
- Local Node tests now include multi-module preflight rollback on missing/circular graphs and stale revisions, deterministic consumer-first disposal, reentrancy safety, and initial forward-reference compilation. They also verify the classic/ESM separation, successful unchanged output after rejected builds, preflight validation of a replacement graph, revision checks, bounded registry entries, and 2000 replacement/dispose operations. A separate Node `--expose-gc` heap experiment samples retained memory over 7000 replacement/re-instantiation operations: this tests Node and controlled cleanup only; **not** proof of bounded heap usage in a long-lived real browser. A real-browser script test passed on GitHub Actions Ubuntu/Chrome (run 38034189246) for two consecutive same-URL patch GETs under CSP without `unsafe-eval`. Locally the available Chromium hangs even on a trivial headless invocation (infrastructure limitation). A further hosted Chrome experiment also passed after 3,000 replacements with exposed GC and `performance.memory`: reported post-GC heap readings were 0.60 MiB across all four windows (workflow run 38034330363, commit ff06cd64). This is bounded-memory evidence for that synthetic browser workload and run, not proof of indefinite leak-free operation with real applications. A new browser harness tests independently loaded clients pinned to content-hashed `jsc` releases, a staged publication gate, retention of old immutable assets, and a service worker waiting for explicit activation after old clients close; this is only a controlled experiment, not a general release/update facility.
- Hot replacement invalidates affected consumers; callers must reacquire their entry module. A batch has all-or-nothing **preflight/definition registration**, but no guarantee that old application state, external side effects or failed cleanup can be undone. No application-state transfer exists.
- The dynamic `<script>` route requires a server for remote updates and an appropriate site CSP; does not bypass CSP to execute arbitrary downloaded text.
- Integrate via existing `mk` process actions only if relevant; tooling/package installation belongs to future `pkg` evaluation and **no product files are changed by this PoC**.

## Browser follow-up experiments (2026-10-10)

- `tests/browser-lifecycle.mjs`: real Chrome DOM listener and timer lifecycle over 1,200 replacement operations. Active listeners fire exactly once, old intervals cease after disposal, invalid transactions leave active instances untouched, and intentionally retained old exports are still callable but their disposed backing data has been cleared. An explicit negative control demonstrates an unregistered listener is **not** cleaned automatically. Post-GC browser heap samples are bounded only for this fixture.
- `tests/browser-releases.mjs`: builds two separate classic `jsc` releases, serves SHA-256-derived immutable asset paths while release HTML/metadata are revalidated, rejects premature publication before staging, keeps an old iframe alive across release publication and checks a new iframe receives the new bundle. A real service worker v2 should remain waiting while v1 clients are present; the fixture explicitly closes old clients before requesting activation. This is **not** an automatic migration protocol, browser-cache universal guarantee or real production service-worker deployment.
- Both experiments require a functioning Chrome/Chromium and execute under `npm run test:browser`; absence of hosted browser validation must be reported as unvalidated, even if syntax checks pass.

## Experimental client-migration and interruption scenario

- `tests/migration.mjs` demonstrates an **application-owned** v1-to-v2 state snapshot conversion using the real classic loader, and rejects incompatible snapshots **before** disposing the running instance. It explicitly demonstrates stale old export handles, stale revision rejection, and a valid replacement whose new factory fails during initialization (no automatic state rollback).
- `tests/browser-multitab.mjs` additionally blocks upgrades when a known peer does not respond within the vote window; a timeout is not consent. This is a test-only fail-closed policy, not crash-proof membership detection.
- `tests/browser-multitab.mjs` exercises two **top-level** Chrome tabs with different session state and real `BroadcastChannel` votes. A dirty peer vetoes migration; after both are ready they independently reload and restore count values through session-local versioned snapshots. The test also simulates interrupted release metadata fetching, a truncated classic-script HTTP patch, failed staging, a rejected premature publish, old immutable-asset retention, and a waiting service-worker update activated only after both tabs move to v2.
- This browser scenario is a **test-only example policy**, not a public API supplied by `JscRuntime` or a general distributed deployment protocol. A peer vote is a moment-in-time observation, not a guaranteed membership/consensus protocol; crashed/unresponsive tabs, split browsers/devices, irreversible side effects and failed migration after reload still need product-level policies. No automatic ESM handling was added.

## Renderer crash and service-worker cache fallback (2026-10-10)

- `tests/browser-multitab.mjs` now causes a separate real Chrome tab renderer to terminate using the DevTools `Page.crash` command. - `tests/browser-offline.mjs` is an **independent real Chrome test** of a release-pinned service worker. The navigation checked is an iframe, not every top-level PWA navigation. The test's fetch-first/cache-fallback policy, cache naming and explicit worker activation belong entirely to its **application fixture**; neither `jsc` nor the independent `loader.js` acquired those responsibilities. ## Whole-browser restart and durable state (2026-10-10)

- `tests/browser-restart.mjs` launches **real Google Chrome**, installs a real service worker with release-pinned Cache Storage, changes application state, and saves count `7` through a strict-durability IndexedDB readwrite transaction. The test then changes live state to `11` **without committing those additional four units**, terminates the complete Chrome process group with `SIGKILL`, and starts a new Chrome process with the **same on-disk user profile**. The backend is deliberately unavailable (HTTP 503, ten refused requests). The page boots again through the cached release pointer and content-addressed classic bundle: saved count `7` is restored, while the in-memory-only count `11` is **not** reconstructed.
- The same test writes an incompatible persisted snapshot with schema `99` through a confirmed IndexedDB transaction. An offline reload refuses to initialize the application with that snapshot, reports `RECOVERY_REQUIRED`, and preserves the incompatible data for inspection. A separate explicit test-user action clears that state and reloads the empty application. This manual reset is intentionally not silent/automatic.
- **Negative evidence:** in the first hosted attempt (run `38046045226`), a `localStorage.setItem()` result was readable before `SIGKILL` but its contents were not found after process restart in this fixture. Do not infer a universal durability hierarchy from one run. The subsequent revised experiment uses an **acknowledged IndexedDB transaction** with `durability:'strict'` as a more explicit persistence boundary. Intermediate revisions `38046166472` and `38046259193` identified browser navigation/harness diagnostic defects before full success; Git was corrected forward.
- **Hosted validation:** [GitHub Actions run 38046328036](https://github.com/massimilianonardi-ai/rumiai-dev-PoCs/actions/runs/38046328036) at code/test commit `cafa5bebcb7ef6ad6b67dcb1245a1857cad879a3` passed the entire Node.js 22 suite, the compiler-only/independent-loader/optional-assembler boundaries, six real Chrome scenarios including the process-kill/restart test, and artifact publication.
- **Limits:** a sudden browser-process SIGKILL is not a disk failure, power loss or transaction-store corruption. Chrome was restarted using the same valid profile and the same browser build in the hosted runner. The origin was reachable but returned HTTP 503; it was not physically disconnected. The app's recovery and state-snapshot policy is **application-owned**, not a feature of `jsc` or `loader.js`. IndexedDB strict durability does not itself prove zero data loss on every platform or guarantee preservation of edits that were never committed.

## Browser offline navigation and release cache pruning (2026-10-10)

- `tests/browser-restart.mjs` now goes beyond an HTTP-503 fallback. After it has recovered a strict IndexedDB snapshot following complete Chrome SIGKILL and restart, it configures Chrome DevTools network emulation to **offline** for the page target, closes the **actual loopback HTTP listener**, and confirms a direct Node HTTP request to the origin fails. Chrome performs a **top-level `Page.navigate`** back to the same application. The installed service worker serves cached HTML, the pinned release pointer and the content-hashed JavaScript, restoring the committed state (7). The test then reopens the listener, disables the DevTools offline override and navigates again; this time the release pointer comes from the live origin. The snapshot incompatibility and explicit manual recovery checks still pass.
- **Important test correction:** initial hosted run [38046765372](https://github.com/massimilianonardi-ai/rumiai-dev-PoCs/actions/runs/38046765372) showed that merely setting the DevTools **page target** offline could leave the service worker able to contact the server: `navigator.onLine` was false but the release pointer came from a live response. The forward correction additionally disconnects the TCP origin and verifies the connection fails. DevTools emulation plus listener shutdown is not the same as turning off the entire host's physical network adapter, and this distinction must remain explicit.
- `tests/browser-offline.mjs` now demonstrates a small **application-owned** release-retention policy. While v1 and v2 remain pinned, a cleanup pass preserves both real Cache Storage entries. Only after v1 clients have migrated and the application releases the v1 pin does another pass delete its cache and **20 synthetic retired-generation caches**; v2 stays cached and usable offline, and an unrelated application cache is not touched. The test demonstrates explicit lifecycle-based bounded cleanup, not automatic peer discovery, all possible quota/eviction behavior or a safe globally coordinated garbage collector.
